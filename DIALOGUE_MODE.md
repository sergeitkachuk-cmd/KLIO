# Диалоговый режим КЛИО

Реализованы два переключаемых интерфейса с общей базой аккаунтов, брендов,
материалов и публикаций. Новые аккаунты начинают с диалога. Существующий
профиль не требуется для обычного вопроса, темы или текста.

Диалоги сохраняются на сервере. КЛИО отвечает на вопросы, предлагает темы,
создаёт и редактирует посты. Карточки можно сохранять в материалы, возвращать
в диалог и открывать в профессиональном редакторе. Ручные правки сохраняются;
конфликты версий показываются пользователю. Публикация открывает существующее
окно подтверждения с выбором канала и времени, без автоматической отправки.
Профиль заполняется после подтверждения, уже заполненные поля сохраняются.

## Развёртывание

1. Проверить состав изменений: в рабочем каталоге есть отдельные ранее
   начатые изменения SEO-аудита, оплаты и авторизации. Они не являются частью
   диалогового режима.
2. Перед изменением рабочей базы сделать резервную копию. Схема добавляет
   `accounts.workspaceMode` и таблицу `dialogueThreads`. Штатный Docker запуск
   проекта применяет схему через `npm run db:push`; проверить diff схемы до
   запуска, особенно при наличии посторонних изменений в рабочем каталоге.
3. Настройки текстового ИИ используются существующие. Один ответ расходует
   одно действие редактирования тарифа, картинка — одну генерацию. Ошибка
   задания возвращает зарезервированный лимит в соответствующем периоде.
4. Изображения требуют настроенного S3-хранилища основного приложения:
   `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`,
   `S3_SECRET_ACCESS_KEY`. Готовые изображения выдаются через `/api/uploads/`
   на домене сайта, браузер клиента не обращается к провайдеру генерации.

### Выбранный вариант: существующий сервис Telegram в Render

Пользователь предпочёл обойтись без второго оплачиваемого сервиса. По
скриншотам `klio-telegram-relay` использует образ
`aiogram/telegram-bot-api:latest`, регион Oregon, без Docker Command.
Подготовлен общий образ Telegram + изображения; инструкции и условия
переключения находятся в `services/klio-images/COMBINED.md`.

Проверенная сборка: `37f83bde0e024f99793ca34a390738b9f59883c0`,
GitHub Actions run `35464765002` завершён успешно. Образ доступен для
анонимного скачивания:
`ghcr.io/sergeitkachuk-cmd/klio-relay:37f83bde0e024f99793ca34a390738b9f59883c0`.
В Timeweb после переключения Render использовать
`KLIO_IMAGE_SERVICE_URL=https://klio-telegram-relay.onrender.com`.
Смена образа в Render и проверка реального Telegram ещё не выполнены.

### Альтернатива: отдельный сервис изображений в Render

`services/klio-images/render.yaml` описывает новый сервис `klio-images`.
Существующий `klio-telegram-relay` продолжает обслуживать Telegram.

Сервис запускается командой `node services/klio-images/server.mjs` из корня
репозитория, Node >=22.13. Настроить в панели Render:

- `OPENAI_API_KEY` — ключ аккаунта с доступом к генерации изображений.
- `KLIO_IMAGE_SERVICE_TOKEN` — случайный секрет длиной не менее 32 символов.
- `KLIO_IMAGE_MODEL` — необязательно, по умолчанию
  `gpt-image-2.5-flare-2026-09-08` (реальная модель OpenAI с 2026-09-08,
  ручное сравнение с `gpt-image-1` в этом же диалоге показало заметно
  более надёжный рендер русского текста на картинке). Взята датированная
  версия, а не «плавающий» алиас `gpt-image-2.5-flare` — у алиаса OpenAI
  может позже незаметно подменить снимок модели, а датированная версия
  гарантированно останется той же, что проверяли. Задавайте вручную
  только если нужно вернуться на `gpt-image-1` или другую модель для
  конкретного деплоя.

Регион размещения и аккаунт должны поддерживаться провайдером API.
В панели основного приложения Timeweb добавить:

- `KLIO_IMAGE_SERVICE_URL` — публичный HTTPS-адрес нового сервиса.
- `KLIO_IMAGE_SERVICE_TOKEN` — тот же секрет, что в Render.

Значения секретов вводить в переменные окружения сервисов, не в Git или чат.
Если основной сервер сам имеет поддерживаемый доступ к API, отдельный
сервис необязателен: при отсутствии URL используется серверный
`OPENAI_API_KEY` основного приложения.

`GET /health` проверяет наличие конфигурации, но не подтверждает успешную
генерацию. После развёртывания проверить реальную картинку из диалога,
сохранение в материалы и загрузку её URL с клиентского устройства без VPN.
Не отправлять тестовые публикации в действующие каналы.

## Проверено локально 19 сентября 2026

- 130 автоматических тестов прошли, ESLint без ошибок, production build прошёл.
- Браузерная проверка с временной PostgreSQL-совместимой базой: темы → пост →
  ручные правки → материалы → возврат в диалог; переключение режимов,
  восстановление после обновления, мобильные светлая и тёмная темы,
  открытие подтверждения публикации. Реальных публикаций не было.
- Отдельная реальная проверка API на вымышленных данных: темы, пост и PNG.
  Рабочая база и клиентские данные при этой проверке не использовались.

Команды: `npm.cmd run test:unit`, `npm.cmd run lint -- --quiet`,
`npm.cmd run build`. Браузерный сценарий:
`node scripts/dialogue-browser-smoke.mjs` при локальном сервере на localhost:3027.
`scripts/dialogue-provider-smoke.mjs --run` выполняет платные реальные запросы;
обычный запуск тестов этого не делает.

Код пока не опубликован на рабочем сайте. Подключение Render/Timeweb и
приёмочная проверка без VPN на рабочем домене остаются отдельным шагом.
